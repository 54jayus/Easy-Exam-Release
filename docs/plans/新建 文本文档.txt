 架构与代码质量评审报告

     Context

     本报告对「智能考务系统」进行全面的架构与代码质量评审。系统由 Electron + Vue 3 前端和 Python 后端组成，通过 stdin/stdout JSON-RPC
     通信。评审目标是识别影响可维护性、安全性、可测试性的问题，并给出可落地的改进方案。

     ---
     一、架构层面问题

     🔴 A1【严重】rpc_server.py 是一个 2465 行的单体巨型模块

     问题：build_dispatch() 函数本身长达 2305 行，包含所有业务逻辑（监考编排、考场编排、打印、授权、AI 助手），所有状态变量以 nonlocal
     闭包形式存在，所有 RPC 处理函数都是嵌套函数。

     影响：
     - 无法对任何单个 RPC 方法写单元测试
     - 任何改动都需要在 2000+ 行中定位
     - 圈复杂度极高（估计 >100）

     改进方案：按业务域拆分为独立模块，每个模块有自己的 Service 类：

     backend/
       services/
         subjects_service.py      # SubjectsService
         proctoring_service.py    # ProctoringService
         rooms_service.py         # RoomsService
         printing_service.py      # PrintingService
         assistant_service.py     # AssistantService
         licensing_service.py     # LicensingService
       state/
         app_state.py             # AppState dataclass（集中状态）
         state_store.py           # 持久化逻辑
       rpc_server.py              # 只做路由分发，<100 行

     重构后 rpc_server.py 示例：
     def build_dispatch(state: AppState) -> dict[str, Callable]:
         subjects_svc = SubjectsService(state)
         proctoring_svc = ProctoringService(state)
         rooms_svc = RoomsService(state)
         printing_svc = PrintingService(state)

         return {
             "subjects_get": subjects_svc.get,
             "subjects_import": subjects_svc.import_from_excel,
             "proctoring_generate_schedule": proctoring_svc.generate_schedule,
             # ...
         }

     ---
     🔴 A2【严重】状态管理混乱：20+ 个 nonlocal 变量

     问题：所有业务状态（subjects、teachers、schedule、rooms、printing）以 nonlocal 闭包变量形式散落在 build_dispatch() 内，没有统一的状态容器。

     影响：
     - 状态变更路径不可追踪
     - 多个函数修改同一变量，容易产生隐式耦合
     - 无法做状态快照或回滚

     改进方案：引入 AppState dataclass 集中管理：

     @dataclass
     class AppState:
         subjects: list[dict] = field(default_factory=list)
         proctoring_teachers: list[dict] = field(default_factory=list)
         proctoring_schedule: list[dict] = field(default_factory=list)
         proctoring_config: dict = field(default_factory=dict)
         rooms_settings: list[dict] = field(default_factory=list)
         rooms_results: list[dict] = field(default_factory=list)
         printing_state: dict = field(default_factory=dict)
         # ...

     ---
     🟡 A3【中】持久化策略：每次状态修改都同步写磁盘

     问题：每个修改状态的 RPC 方法末尾都调用 _save_state()，同步写 JSON 文件，无文件锁，无批量合并。

     影响：
     - 高频操作（如逐行导入）会产生大量磁盘 I/O
     - 多进程访问可能导致文件损坏

     改进方案：
     class StateStore:
         def __init__(self, path: str):
             self._path = path
             self._dirty = False
             self._lock = threading.Lock()

         def mark_dirty(self):
             self._dirty = True

         def flush(self):
             """在 RPC 响应发出前统一调用一次"""
             if self._dirty:
                 with self._lock:
                     self._write()
                     self._dirty = False

     ---
     🟡 A4【中】前端 preload.ts 暴露了完整 ipcRenderer，无通道白名单

     问题（apps/desktop/electron/preload.ts）：
     // 当前：任意通道都可调用
     ipcRenderer.invoke(channel: string, ...args: any[])

     渲染进程可以调用 spawn_python、kill_python、write_python 等危险操作。

     改进方案：
     const ALLOWED_CHANNELS = [
       'spawn_python', 'write_python', 'kill_python',
       'dialog:open', 'dialog:save', 'open_path',
       'assistant:open', 'assistant:close',
       'backend_project_root', 'app_exe_dir',
     ] as const

     contextBridge.exposeInMainWorld('electron', {
       ipcRenderer: {
         invoke(channel: typeof ALLOWED_CHANNELS[number], ...args: any[]) {
           if (!ALLOWED_CHANNELS.includes(channel)) {
             throw new Error(`IPC channel not allowed: ${channel}`)
           }
           return ipcRenderer.invoke(channel, ...args)
         }
       }
     })

     🟡 B6【中】错误处理三种模式混用

     问题：rpc_server.py 中同时存在：
     1. return _reply_err("message") — 大多数函数
     2. return {"error": msg} — 部分函数（格式不同！）
     3. raise ValueError(...) — 少数函数

     改进方案：统一使用 _reply_err，在 main() 的顶层 try/except 捕获所有未处理异常：
     def main():
         dispatch = build_dispatch()
         for line in sys.stdin:
             try:
                 req = json.loads(line)
                 handler = dispatch[req["method"]]
                 result = handler(req.get("params", {}))
                 print(json.dumps({"ok": True, "result": result, "id": req["id"]}))
             except KeyError:
                 print(json.dumps({"ok": False, "error": f"未知方法: {req.get('method')}", "id": req.get("id")}))
             except Exception as e:
                 logger.exception("RPC 处理异常")
                 print(json.dumps({"ok": False, "error": str(e), "id": req.get("id")}))

     🟡 B7【中】assistant/core/zhipu_client.py 中 429 错误未重试

     问题（第 108-124 行）：HTTP 错误统一抛出，但 429（限流）应该指数退避重试。

     改进方案：
     import time

     def _request_with_retry(self, payload, max_retries=3):
         for attempt in range(max_retries):
             try:
                 return self._do_request(payload)
             except ZhipuApiError as e:
                 if "429" in str(e) and attempt < max_retries - 1:
                     time.sleep(2 ** attempt)  # 1s, 2s, 4s
                     continue
                 raise

     🟡 B9【中】pythonBackend.ts IPC 监听器未清理，可能内存泄漏

     问题（apps/desktop/src/lib/pythonBackend.ts 第 82-96 行）：每次调用 start() 都会添加新的 python-stdout/python-stderr 监听器，旧的不会移除。

     改进方案：
     private stdoutListener: ((e: any, data: string) => void) | null = null

     private registerListeners(electron: any) {
       this.removeListeners(electron)  // 先清理
       this.stdoutListener = (_: any, data: string) => this.onStdout(data)
       electron.ipcRenderer.on('python-stdout', this.stdoutListener)
     }

     private removeListeners(electron: any) {
       if (this.stdoutListener) {
         electron.ipcRenderer.off('python-stdout', this.stdoutListener)
         this.stdoutListener = null
       }
     }
