# Easy Exam 自动更新方案设计

## 1. 背景

对于桌面软件来说，“自动检测更新”的核心思路并不复杂：

1. 客户端拿到自己当前版本号
2. 去远程地址请求“最新版本信息”
3. 比较本地版本和远程版本
4. 如果远程版本更高，则提示用户下载并安装新版本

这里的“远程地址”不一定是传统意义上的自建服务器，也可以是：

- GitHub Releases
- GitHub Pages
- 对象存储静态文件
- 其他可公开访问的静态托管服务

对于独立开发项目，最重要的是：

- 成本低
- 维护简单
- 足够稳定
- 后续容易扩展

## 2. 适合本项目的推荐方案

针对当前 Easy Exam 的 Electron 架构，推荐采用：

**GitHub Releases + GitHub Pages + 客户端自定义更新逻辑**

这是当前最适合独立开发者的平衡方案。

### 2.1 组成

分成两部分：

1. **安装包存放**
   - 放在 GitHub Releases
   - 每个版本发布一个 Windows 安装包

2. **更新元数据**
   - 放在 GitHub Pages 或其他静态托管地址
   - 客户端只请求一个 `latest.json`

### 2.2 优点

- 不需要自建服务器
- 不需要维护数据库或后端 API
- 更新源结构简单，容易调试
- 客户端逻辑完全可控
- 适合先做“完整安装包更新”

### 2.3 不建议第一版就做的内容

- 增量更新
- 静默安装
- 强制更新
- 灰度发布
- 多渠道更新策略

第一版只做“检查更新 + 下载完整安装包 + 提示安装”即可。

## 3. 远程更新源设计

### 3.1 GitHub Releases 负责什么

GitHub Releases 用来存放真正的安装包，例如：

- `EasyExam-Setup-3.5.0.exe`

建议发布时：

- 使用规范的 tag，例如 `v3.5.0`
- 每个 release 上传完整安装包
- release 描述里填写更新说明

### 3.2 GitHub Pages 负责什么

GitHub Pages 用来托管一个稳定的静态 JSON，例如：

- `https://<your-pages-domain>/update/win/latest.json`

客户端只需要访问这个 JSON，就能知道是否有更新。

### 3.3 推荐的 `latest.json` 结构

```json
{
  "version": "3.5.0",
  "releaseDate": "2026-05-26",
  "notes": [
    "新增整套方案导出与导入",
    "统一本地运行环境配置",
    "修复状态恢复问题"
  ],
  "mandatory": false,
  "url": "https://github.com/54jayus/Easy-Exam/releases/download/v3.5.0/EasyExam-Setup-3.5.0.exe",
  "sha256": "安装包哈希值，可选但强烈建议保留",
  "size": 123456789
}
```

### 3.4 字段说明

- `version`
  - 最新版本号
- `releaseDate`
  - 发布时间
- `notes`
  - 更新说明数组
- `mandatory`
  - 是否强制更新
- `url`
  - 安装包下载地址
- `sha256`
  - 用于校验文件完整性
- `size`
  - 安装包大小，便于前端显示

## 4. 客户端更新流程

### 4.1 推荐时机

建议提供两种检查方式：

1. 启动后自动检查
2. 用户手动点击“检查更新”

启动自动检查建议延迟 3 到 5 秒，避免应用刚启动时打断主流程。

### 4.2 完整流程

1. 获取本地版本号
2. 请求远程 `latest.json`
3. 比较版本号
4. 若有新版本，弹出更新说明
5. 用户确认后下载完整安装包
6. 下载完成后提示安装
7. 退出当前应用并启动安装包

### 4.3 本地版本获取

Electron 中推荐直接使用：

- `app.getVersion()`

### 4.4 版本比较

不要直接使用字符串比较，建议采用统一的版本比较规则。

推荐未来逐步使用语义化版本：

- `3.4.0`
- `3.4.1`
- `3.5.0`

当前项目若继续保留类似 `3.4.0422` 的格式，也可以支持，但需要明确比较规则。

## 5. Windows 安装与更新方式

### 5.1 第一版推荐方式

Windows 下最稳妥的方式是：

1. 下载完整安装包 `.exe`
2. 下载完成后提示用户“立即安装”或“稍后安装”
3. 若立即安装：
   - 先关闭当前 Electron 应用
   - 再启动安装包

### 5.2 不建议第一版做的方式

- 在应用运行中直接覆盖自身文件
- 复杂的增量 patch
- 静默覆盖安装

这些都比完整安装包方案更复杂，也更容易引入兼容问题。

## 6. 安全性建议

自动更新至少应补这两层保护：

### 6.1 固定更新源

客户端不要让用户随意输入更新地址。  
建议在代码里固定更新源域名或配置源。

### 6.2 校验安装包

下载完成后：

1. 计算文件 `sha256`
2. 与 `latest.json` 中的 `sha256` 比较
3. 校验通过才允许安装

这能显著减少文件损坏或被替换带来的风险。

## 7. 适合 Easy Exam 的代码结构建议

建议把自动更新逻辑单独收口，不要散落在页面里。

### 7.1 推荐新增文件

Electron 主进程侧：

- `frontend/electron/updater.ts`

前端渲染层：

- `frontend/src/lib/updater.ts`
- `frontend/src/types/update.ts`

### 7.2 职责划分

**主进程负责：**

- 获取当前版本
- 请求远程更新信息
- 下载安装包
- 启动安装包

**渲染进程负责：**

- 提供“检查更新”按钮
- 弹出更新说明
- 显示下载进度
- 让用户决定立即安装或稍后处理

## 8. 推荐的 IPC 设计

可以新增一组更新相关 IPC：

- `update:check`
  - 检查是否有新版本
- `update:download`
  - 下载更新包
- `update:install`
  - 启动安装包并退出应用
- `update:status`
  - 查询或推送下载进度

推荐返回结构示例：

```json
{
  "currentVersion": "3.4.0",
  "latestVersion": "3.5.0",
  "hasUpdate": true,
  "mandatory": false,
  "notes": [
    "新增整套方案导出与导入"
  ],
  "url": "https://..."
}
```

## 9. UI 建议

第一版建议把入口放在以下位置之一：

1. 工作台页面右上角
2. 设置菜单中
3. “关于软件”对话框内

建议最少提供：

- “检查更新”按钮
- 当前版本号显示
- 有更新时的更新说明弹窗
- 下载进度显示

## 10. 推荐发布流程

每次发布新版本时，可以按以下流程执行：

1. 修改应用版本号
2. 构建新的 Windows 安装包
3. 发布到 GitHub Releases
4. 更新 GitHub Pages 上的 `latest.json`
5. 确认下载地址可访问
6. 让客户端启动后自动检查到新版本

## 11. 公开仓库与私有仓库的区别

### 11.1 公开仓库

如果项目仓库是公开的：

- GitHub Releases 资产下载最方便
- GitHub Pages 也很容易直接使用
- 对独立开发者最友好

### 11.2 私有仓库

如果项目仓库是私有的：

- 客户端直接下载 GitHub 私有 Release 资产会涉及鉴权
- 不适合匿名客户端直接下载

此时更建议：

- 安装包仍放公开下载地址
- 更新 JSON 也放公开静态地址
- 仓库代码可以继续私有

## 12. 第一版落地范围建议

建议第一版只覆盖以下能力：

1. 手动“检查更新”
2. 启动后自动检查
3. 显示更新说明
4. 下载完整安装包
5. 下载完成后提示安装

这样复杂度可控，且已经足够满足大多数独立项目需求。

## 13. 后续可扩展方向

如果第一版稳定，后续可以再扩展：

- “忽略此版本”
- “稍后提醒”
- 静默下载
- 更新历史页面
- 强制更新
- 灰度更新
- 多平台更新源

## 14. 适合当前项目的结论

对 Easy Exam 来说，最推荐的自动更新路线是：

**GitHub Releases 存安装包 + GitHub Pages 放 `latest.json` + Electron 客户端自己实现更新检查与下载安装**

这是当前最符合以下条件的方案：

- 独立开发项目
- 不想维护自建服务器
- 主要面向 Windows 桌面端
- 需要稳定、直观、易维护的更新机制

## 15. 后续实现建议顺序

真正开始开发时，建议按下面顺序推进：

1. 先定义 `latest.json` 协议
2. 再实现主进程 `update:check`
3. 再增加前端“检查更新”按钮
4. 再实现下载进度和安装逻辑
5. 最后再考虑更高级的更新体验
